## EXPLOIT DEVELOPMENT LIFECYCLE

### Phase 1 — Reconnaissance (MITRE TA0043)
```
Active Techniques:
  - Port scanning (nmap, masscan, rustscan)
  - Service enumeration (version detection, banner grabbing)
  - Web technology fingerprinting (Wappalyzer, WhatWeb, BuiltWith)
  - Subdomain enumeration (subfinder, amass, certificate transparency)
  - DNS enumeration (dnsrecon, zone transfer attempts)
  - Cloud asset discovery (cloud_enum, ScoutSuite)
  - API endpoint discovery (feroxbuster, ffuf, dirsearch)

Passive Techniques:
  - WHOIS lookup (historical + current)
  - Shodan / Censys / ZoomEye queries
  - GitHub dorking (secrets, configs, internal paths)
  - Wayback Machine (historical endpoints)
  - Social media OSINT (employee roles, tech stack hints)
  - Job posting analysis (revealed tech stack)
  - SSL certificate transparency logs

Output: Target profile document (attack surface map)
```

### Phase 2 — Vulnerability Discovery (MITRE TA0042)
```
Automated Scanning:
  - Web: Nuclei, Burp Suite (authenticated), ZAP, Nikto
  - Network: OpenVAS, Nessus (if licensed), NSE scripts
  - Cloud: Prowler, ScoutSuite, cloudsplaining
  - Container: Trivy, kube-hunter, kube-bench
  - Code: Semgrep, CodeQL, SonarQube (SAST)
  - Dependency: Snyk, OWASP Dependency Check (SCA)
  - API: Postman collection fuzzing, Swagger endpoint analysis

Manual Testing:
  - Business logic flaws (workflow bypass, race conditions)
  - Authentication/Authorization (JWT manipulation, IDOR, privilege escalation)
  - Input validation (SQLi, XSS, SSTI, SSRF, XXE, command injection)
  - Deserialization (Java, PHP, Python pickle, Node.js)
  - Cryptographic weaknesses (weak ciphers, hardcoded keys, padding oracle)

Chaining:
  - Low severity × N → high severity exploitation path
  - Document chain: vuln A enables vuln B enables full compromise
```

### Phase 3 — Exploit Development
```
Proof of Concept:
  1. Reproduce vulnerability in isolated test environment
  2. Develop minimal PoC (proves impact, minimal payload)
  3. Test against target (within scope only)
  4. Document: preconditions, steps, impact, remediation

Weaponization:
  1. Add reliability (retry logic, fallback methods)
  2. Add stealth (traffic obfuscation, timing randomization)
  3. Add persistence hooks (if within scope)
  4. Package as standalone script (Python/Bash/PowerShell)
  5. Test against multiple target configurations

Types of Exploits:
  - Web: SQLi → RCE, SSRF → metadata exfil, SSTI → shell, XXE → LFI
  - Network: Buffer overflow, format string, logic bypass
  - Binary: ROP chains, ret2libc, heap exploitation, format string
  - Crypto: Padding oracle, nonce reuse, weak random, hash length extension
  - Cloud: AssumeRole chaining, metadata exfil, storage misconfiguration
  - Container: Escape via socket mount, cap_sys_admin, cgroup breakout
  - Active Directory: Kerberoasting, AS-REP roasting, DCSync, NTLM relay
```

### Phase 4 — Delivery & Execution (MITRE TA0002)
```
Delivery Vectors:
  - Phishing email (spear, whaling, credential harvesting)
  - Watering hole attack
  - Malicious document (macro, DDE, OLE, formula injection)
  - USB drop (Rubber Ducky, Bash Bunny)
  - Supply chain compromise (dependency confusion, typosquatting)
  - Drive-by download (browser exploit, malvertising)
  - Physical access (explicit authorization required)

Payload Types:
  - Staged: small dropper → fetch full payload
  - Stageless: self-contained, larger on disk
  - Reflective: in-memory only, no disk footprint
  - Fileless: registry, WMI, scheduled task persistence

Initial Access Techniques:
  - Valid accounts (password spray, credential stuffing)
  - External remote services (RDP, SSH, VPN exploitation)
  - Public-facing application exploit (CVE exploitation)
  - Trusted relationship abuse (partner VPN, cloud federation)
```

### Phase 5 — Post-Exploitation
```
Objectives (scope-dependent):
  - Persistence (MITRE TA0003)
  - Privilege Escalation (MITRE TA0004)
  - Defense Evasion (MITRE TA0005)
  - Credential Access (MITRE TA0006)
  - Discovery (MITRE TA0007)

Persistence Methods:

Privilege Escalation:
```

## C2 (COMMAND & CONTROL) PATTERNS

### C2 Architectures
```
1. DIRECT (simplest, most detectable)
   implant ↔ C2 server (TCP/HTTP/HTTPS/DNS)
   Use: lab testing, short engagements
   Tools: Metasploit, Empire, Covenant, Sliver

2. REDIRECTOR CHAIN (medium stealth)
   implant → redirector1 → redirector2 → C2 server
   Use: longer engagements, production red teams
   Tools: Apache/Nginx reverse proxy, Socat, SSH tunnels, Cloudflare CDN

3. PEER-TO-PEER (high stealth)
   implants communicate with each other, one egress point
   Use: air-gapped network bridging, long-term persistence
   Tools: custom P2P protocol, SMB named pipes, internal DNS

4. DOMAIN FRONTING (high stealth, high complexity)
   implant → CDN (Cloudflare/Fastly/AWS CloudFront) → C2
   Use: bypassing network monitoring, blocked C2 domains
   Tools: Cobalt Strike Malleable C2, custom fronting profiles

5. SOCIAL MEDIA / CLOUD C2 (emerging pattern)
   implant ↔ Twitter/Discord/GitHub/GDrive/Notion → C2 operator
   Use: blending into normal traffic, hard to block
   Tools: custom API-based channels, dead drop resolvers
```

### C2 Communication Profiles
```
HTTPS (most common):
  - Mimics legitimate web traffic (e.g., GET /api/status HTTP/1.1)
  - Domain fronting compatible
  - TLS certificate generation (Let's Encrypt automation)
  - Malleable C2 profiles (Cobalt Strike)

DNS:
  - TXT/MX/CNAME record tunneling
  - Low bandwidth (sufficient for commands, not file exfil)
  - Bypasses most firewalls (DNS often unfiltered)
  - Detection: unusual DNS query patterns, large TXT records

HTTP/3 (QUIC):
  - Emerging, less inspected by security tools
  - Bypasses HTTP/2-specific inspection
  - Limited tool support (custom required)

WebSocket:
  - Long-lived, bidirectional
  - Blends with modern web apps
  - Harder to detect than polling-based HTTP C2

ICMP:
  - ICMP tunneling (ptunnel, icmpsh)
  - Very low bandwidth, highly suspicious if monitored
  - Use: last-resort when all TCP/UDP blocked
```

### C2 Infrastructure Deployment
```
Automated deployment pipeline:
  1. Terraform/Pulumi: provision VPS, DNS, CDN
  2. Ansible: configure redirectors, deploy C2 framework
  3. Certbot: auto-TLS with Let's Encrypt
  4. Docker: containerized C2 + redirectors
  5. Monitoring: uptime, bandwidth, implant check-in rate

Provider rotation:
  - DigitalOcean, Vultr, Linode, AWS Lightsail, Azure, GCP
  - Rotate every N days (configurable)
  - Pre-warm redirector domains (age domains before use)

Hardening:
  - C2 server: IP whitelist (only redirector IPs can reach)
  - Redirectors: DDoS protection, CDN
  - Logs: minimal retention, encrypted at rest
  - Kill-switch: auto-destroy on detection signal
```

## PAYLOAD GENERATION

### Payload Pipeline
```
INPUT: target profile (OS, arch, AV/EDR, network egress)
  ↓
SELECT: payload type (staged/stageless, language)
  ↓
GENERATE: shellcode/payload from template
  ↓
OBFUSCATE: encode, encrypt, pack
  ↓
TEST: against local detection (Defender, ClamAV, YARA)
  ↓
DELIVER: execute on target (within scope)

Supported Payload Types:
  - Windows: .exe, .dll, .ps1, .vbs, .hta, .msi, .lnk
  - Linux: ELF binary, .so shared object, .py, .sh, .pl
  - macOS: Mach-O, .app bundle, .pkg, .scpt (AppleScript)
  - Cross-platform: Python, Go, Rust, JavaScript (Node.js)
  - Web: PHP webshell, JSP, ASPX, CFM
  - Mobile: Android APK (if scope includes mobile)
```

### Obfuscation & Evasion Techniques
```
Code-Level:
  - String encryption (XOR, AES, RC4)
  - Control flow flattening
  - Dead code insertion
  - API hashing (resolve at runtime, not import table)
  - Syscall stubs (direct syscalls, bypass userland hooks)
  - Reflective DLL injection (no LoadLibrary)
  - Process hollowing / process doppelganging
  - ETW patching (disable Event Tracing for Windows)

Binary-Level:
  - Packer/compressor (UPX → custom packer)
  - Entry point obfuscation
  - Import address table (IAT) camouflage
  - Section manipulation
  - Code signing (stolen/valid certificates — operator risk)
  - Binary padding

Network-Level:
  - Traffic mimicry (HTTPS to CDN endpoints)
  - Chunked transfer encoding
  - Base64/hex encoding
  - Custom encryption (avoid standard TLS fingerprints)
  - Jitter (random sleep between beacons)
  - Domain rotation (DGA — Domain Generation Algorithm)

Testing Pipeline:
  1. VirusTotal (private upload) — scan score
  2. AntiScan.Me — detection rate
  3. Local VM: Defender + common AV
  4. YARA scanning against known rules
  5. EDR simulation (if EDR profile available)
```

## OPSEC (OPERATIONAL SECURITY)

### Pre-Engagement OPSEC
```
Identity:
  - Use burner infrastructure (no personal accounts)
  - VPN/proxy chain for all recon traffic
  - No personal devices on engagement network
  - Separate browser profile for engagement research

Infrastructure:
  - Domain privacy (WHOIS guard)
  - CDN fronting (hide origin server)
  - No cross-contamination between engagements
  - Separate email, domains, VPS per engagement
  - Payment: crypto for infra, no personal cards

Credentials:
  - No password reuse across engagements
  - Password manager per engagement
  - No operator personally identifiable information (PII) in payloads
```

### During-Engagement OPSEC
```
Network:
  - Rate limit scanning (avoid IDS triggers)
  - Randomize timing (jitter between requests)
  - Respect robots.txt (optional, depends on scope)
  - Use target's own IP ranges when possible (cloud metadata)

Artifacts:
  - Clean up payloads after use
  - Remove persistence mechanisms on engagement end
  - Log all changes for rollback
  - Securely delete all collected data post-engagement

Communication:
  - Separate comms channel from target's infrastructure
  - Encrypted channels for team communication (Signal, Matrix)
  - No discussion of engagement on personal devices/channels
```

### Post-Engagement OPSEC
```
Data Handling:
  - Encrypt all collected data at rest
  - Delete raw data after report delivery (unless retention specified)
  - Secure report delivery (encrypted, authenticated)
  - Report redacted of unnecessary operator-specific details

Cleanup:
  - Destroy engagement VPS/domains
  - Rotate any compromised credentials (target-side)
  - Remove backdoors, accounts, persistence
  - Verify cleanup with target administrator

Retention:
  - Report: retained per agreement (typically 1 year)
  - Raw data: deleted within 30 days
  - Logs: minimal retention for legal protection only
```

## PHISHING FRAMEWORKS

### Phishing Campaign Automation
```
1. Template Engine
   - HTML email templates (responsive, realistic)
   - Landing page clones (login portals, SSO pages)
   - Document templates (invoice, HR, IT notifications)

2. Target Management
   - CSV import (email, name, role, department)
   - Group segmentation (by department, seniority, tech-savviness)
   - Staggered sending (avoid spam detection, appear organic)

3. Payload Integration
   - Attachment: malicious doc, ISO, ZIP with shortcut
   - Link: credential harvesting, drive-by download, MFA relay
   - QR code phishing (quishing)
   - SMS phishing (smishing) — if scope includes
   - Voice phishing (vishing) landing page — if scope includes

4. Campaign Tracking
   - Email opened (tracking pixel — privacy consideration)
   - Link clicked (timestamp, IP, user-agent)
   - Credential submitted (username, password, MFA code)
   - Payload executed (implant check-in)
   - Success rate per template / per segment

5. MFA Bypass (if within scope)
   - Evilginx-style transparent proxy (session cookie capture)
   - MFA fatigue / push notification bombing
   - SIM swap awareness (out of scope, flag to target)

6. Post-Phishing
   - Auto-generate report: delivery rate, open rate, click rate, credential rate
   - Recommendations: awareness training targets, technical controls
```

### Phishing Safety Rails
```
- Sending domain: spoof-proofed (SPF/DKIM/DMARC properly configured)
- Recipient consent: explicit authorization from target organization
- NO real credential storage: credentials captured → encrypted → auto-deleted after report
- NO production impact: link to test/staging portal, not production login
- Landing page: clearly labeled as "security test" after credential entry
- Campaign kill-switch: instant takedown if any issue reported
```
